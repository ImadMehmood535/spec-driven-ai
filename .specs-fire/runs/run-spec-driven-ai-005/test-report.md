## Live Verification — the D-8 cycle

This is the behaviour a naive implementation gets wrong, so it was driven end to end:

```
POST /role/1/permission {"permissionIds":[1,2,3]}   → 201 {"assigned":[1,2,3]}
GET  /role/1/permission                             → 3 items, all ACTIVE

DELETE /role/1/permission/2                         → 200 {"linkStatus":"INACTIVE"}
  DB:  id 1 | perm 1 | ACTIVE
       id 2 | perm 2 | INACTIVE      <- row survived, not deleted
       id 3 | perm 3 | ACTIVE
GET  /role/1/permission                             → active ids [1, 3]

POST /role/1/permission {"permissionIds":[2]}       → 201   <- the critical case
  DB:  id 2 | perm 2 | ACTIVE        <- SAME row reactivated
       total rows: 3                 <- not 4; no UNIQUE violation
```

A plain "insert on assign" would fail here with
`duplicate key value violates unique constraint "RolePermission_roleId_permissionId_unique"`
the first time an operator removed a permission and added it back.

### Error paths, all live

```
assign already-active      → 409      assign to missing role     → 404
assign missing permission  → 404      empty permissionIds        → 400
remove unassigned          → 404      list for missing role      → 404
?includeInactive=true      → 3 items (removed link visible)
```
