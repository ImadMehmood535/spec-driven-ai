## Correctness review of D-8 — the part most likely to be wrong

**"Already assigned" means already assigned *and active*.** The handler compares against
`activePermissionIds`, not all links. An inactive row is not a conflict; it is the row to
reactivate. Had this compared against all rows, re-assignment would have returned 409 forever
and the feature would be unusable.

**Reactivation happens inside the transaction**, in `assignMany`: find the row, `update` it to
`ACTIVE`, else insert. Checked that the find is transaction-scoped — otherwise a concurrent
assign could read a stale absence and attempt a duplicate insert.

**Removal is idempotent.** Removing an already-removed permission returns 200 with
`INACTIVE` rather than failing, because the operator's intent is already satisfied.

**A missing role on list is 404, not an empty array.** "Role does not exist" and "role has no
permissions" are different answers, and an empty array for a typo'd id would mislead.

## Observations — no action taken

**`DELETE` is used for relationship removal.** It is the correct HTTP verb for "remove this
permission from this role", and it does not delete a row. The controller comment and the
response's `linkStatus: "INACTIVE"` make that visible to API consumers, and the Swagger summary
says "deactivates the link".

**`activePermissionIds` returns ids, not aggregates.** A read-shaped method on the write port.
Justified: the handler needs it for a conflict check inside a command, and routing that through
the query side would make a command depend on the read model.

**Permission existence is checked in a loop, one query per id.** Fine for the handful of
permissions an operator assigns at once; would want a single `IN` query if this ever took
hundreds. Not worth pre-optimising.

**The `RolePermissionQueries` join requires `PermissionModel`** to be registered in the
persistence module, which it now is. If a future slice forgets that, the join silently returns
nothing — the live list check is what would catch it.
