## Credential handling review

**Hashing is outside the aggregate.** `User.create` takes a hash, never a plaintext. Correct:
hashing is async and belongs to the application layer, and it means no domain object can hold
plaintext that a snapshot or log could capture.

**The write path is named for the hash.** `changePasswordHash`, not `changePassword`. A caller
cannot hand the aggregate an unhashed value without it reading obviously wrong.

**The read model omits the field entirely** and `UserQueries` selects an explicit attribute
list rather than excluding columns. A future column therefore cannot leak by default — the
opposite posture to `attributes: { exclude: [...] }`, which fails open.

**Ordering is deliberate.** Password length, then role existence, then uniqueness, then hashing.
A rejected request never pays for a cost-12 hash, and a duplicate email is reported before any
hashing work.

**The update route has no password field.** Verified by a test that sends a stray `password` in
a general PATCH body and asserts the resulting command has no such key.

## Standards Compliance

Follows the established slice pattern: thin controller, command handlers on write ports, query
handlers on read ports, validation in the aggregate, `Symbol` tokens, no `*Model` outside
`domain`/`infrastructure`, Swagger complete, no delete route.

## Observations — no action taken

**Password minimum is 8 characters**, chosen here rather than specified anywhere. `docs/scope.md`
sets no password policy, so this is the weakest defensible default rather than a decision the
spec made. Worth revisiting if a policy is ever stated — complexity rules, rotation, and history
are all absent and all out of scope today.

**`passwordHash` has a public getter.** Needed so the repository can persist it. The alternative
— a repository reaching into private state — would be worse. The read model's omission is what
actually protects it.

**Email is lowercased, username is not.** Emails are case-insensitive in practice; usernames are
a deliberate identity choice. Both are trimmed. The uniqueness checks normalise the same way the
aggregate does, so `Ahmed@Example.COM` collides with `ahmed@example.com` as it should.

**`GetUsersResponse` reuses `GetUserResponse` for its items** rather than declaring a parallel
item class. The shapes are genuinely identical here, unlike the permission slice where a
separate item class exists — worth collapsing that one later for consistency.
