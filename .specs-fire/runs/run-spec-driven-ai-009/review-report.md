# Code Review: Seeds

Creates the most privileged account in the system, so the review focused on what could go wrong
on a re-run and on whether a default credential could exist.

## Security review

**No default credentials, verified by running without them.** All three admin variables are
required and the seeder throws naming the missing ones. A default admin password is a backdoor in
every environment that forgot to override it, and the only way to be sure one does not exist is
to try.

**A re-run cannot take over a live account.** The existing-user branch updates the role and
status but explicitly leaves `passwordHash` untouched, and the hash was compared byte-for-byte
across three runs. Without that, any routine deploy would silently reset the administrator's
password to whatever the deploy environment held.

**FR-S7 verified through resolution rather than the insert list.** Asking the seeder whether it
inserted what it meant to insert proves nothing. The check resolves the admin's permissions via
the same query route guards will use, and compares the count against the permission table.

**Links are computed at run time.** A hard-coded list would go stale the moment a permission was
added, leaving the administrator locked out of new routes while the seed still reported success.
Verified by adding a 19th permission and re-seeding.

**Reactivation is handled.** A deactivated seeded permission, role, or link is set back to
`ACTIVE`. Without it, a seed would appear to succeed while leaving a catalogue entry dead — and
for links, `UNIQUE(roleId, permissionId)` means an insert would fail outright (D-8).

## Observations — no action taken

**The admin seeder's `down` deletes by email.** It reads `SEED_ADMIN_EMAIL` and no-ops if unset,
so `seed:undo` in an environment without the variable leaves the admin in place rather than
guessing. Deliberate, though it does mean undo is environment-dependent.

**`down` on the permission seeder deletes rows.** That is a seeder, not a migration, and D-5
governs the API rather than administrative tooling — but it will fail if a role still references
a permission, thanks to `ON DELETE RESTRICT`. That is the correct failure: undoing a seed should
not silently strip grants.

**Four seeders rather than one.** A failure is attributable to a step, and each is re-runnable.
The observed partial state after the intentional credential failure (permissions and role
present, user absent) is exactly the intended behaviour.

**`SEED_ADMIN_FIRST_NAME`/`LAST_NAME` have defaults** ("Platform"/"Administrator") while the
credentials do not. Names are not secrets; a default there is convenience, not risk.
