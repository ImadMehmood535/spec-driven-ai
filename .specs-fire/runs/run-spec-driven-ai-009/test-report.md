## Live Verification

**Fails without credentials — no default admin exists:**

```
$ env -u SEED_ADMIN_EMAIL -u SEED_ADMIN_USERNAME -u SEED_ADMIN_PASSWORD npm run seed
Seed failed: SEED_ADMIN_EMAIL, SEED_ADMIN_USERNAME, SEED_ADMIN_PASSWORD must be set.
The first administrator has no default credentials by design.
```

State after that failure: 18 permissions, 1 role, 18 links, **0 users** — the earlier seeders
completed and the admin was not created. Correct for ordered seeders, and harmless because
re-running completes the remainder.

**Idempotency across three runs:**

```
run 1:  perms 18 | roles 1 | links 18 | users 1
run 2:  perms 18 | roles 1 | links 18 | users 1
run 3:  perms 18 | roles 1 | links 18 | users 1
admin password hash: UNCHANGED (byte-identical before and after)
```

**FR-S7 verified through resolution, not the insert list:**

```
resolved for admin: 18    permissions in table: 18
```

That distinction matters: comparing the seeder's own insert list against itself would prove
nothing. This asks the real resolution query — the same one route guards will use — what the
admin actually holds.

**FR-S7 resilience** — the reason links are computed rather than hard-coded:

```
add a 19th permission via the API, re-run the seed
→ admin now holds: 19 | includes the new one: true
```

**The seeded admin can actually log in** (this is what closes the §2 bootstrap problem):

```
POST /auth/login {"identifier":"admin@developer.local","password":…}  → 200 + token
token claims: role "Developer Admin", permissions: 18
```

Login also works with the username, and the token carries the full set — so the administrator
can reach every route the moment `route-protection` lands.
