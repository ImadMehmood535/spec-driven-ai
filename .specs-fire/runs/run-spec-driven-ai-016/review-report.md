# Code Review: User Management Screens

The only screen handling credentials, so the review weighted that first.

## Findings Fixed

None. Built by hand rather than by substitution, which is why the defects of runs 004 and 015 did
not recur — a deliberate choice, since this screen has no analogue in the other two.

## Credential review

**The password is submitted and never rendered.** Two tests assert `container.textContent` does
not contain the value after submit — on create and on change. Toasts name the user, never the
credential.

**An edit carries no password at all.** Not an empty string, not undefined-but-present: the key is
absent from the submission. A test uses `expect.not.objectContaining` to pin that.

**Changing a password is its own dialog** (D-9), matching the API's own separation. No
current-password challenge, because this is an administrator acting on someone else's account,
not a self-service reset — asserted by the absence of such a field.

**`autoComplete="new-password"`** on both password inputs, so a browser does not offer the
administrator's own saved credential.

**The read model has no hash**, confirmed live: `GET /user` contains zero occurrences of
`passwordHash`. The backend guarantees it (run 006); this verifies the guarantee end to end.

## The two-unique-fields problem

Roles and permissions blanket-attribute a 409 to `name` because they have one unique field. This
form cannot, and does not. It relies on `api-error.ts`'s inference, which works because the API's
messages contain the words "email" and "username".

That completes the pattern the last three runs established:

- **One unique field** → the form attributes (permissions, roles)
- **Several** → the API names it and generic inference suffices (users)

If a future form has several unique fields *and* messages that do not name them, it will need the
API to change, not the UI to guess.

## One role per user, made visible

**Wording carries the constraint.** "Assign role" when none, "Change role" when one is set. The
dialog says choosing another *replaces* the current one, and the current role is marked with a
check and disabled. A multi-select would have implied a capability §6 excludes.

**A user with no role reads "No role"**, not an empty cell — which would read as missing data
rather than as FR-AC4's actual meaning: they hold nothing.

## Observations — no action taken

**The role dialog lists up to 50 roles with search.** Same shape as the permission assignment
view; the same paging caveat applies if roles ever number in the hundreds.

**Creation always sends `roleId: null`.** A role is assigned afterwards through its own dialog.
Combining them would put two decisions in one form; the API allows either.

**The list is not filtered by role or status in the UI** although the API and the hook both
support it. The `toolbar` slot exists for exactly that, and adding it is a small change — but
`docs/scope.md` asks only that users be viewable, and I did not want to invent filters the scope
did not call for.

**`ChangePasswordDialog` resets on close** via an effect keyed on `user`, with an eslint
exhaustive-deps suppression and a comment. Including the mutation object in the deps would reset
it mid-flight.
