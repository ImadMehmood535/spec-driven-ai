## What differed from the other two screens

**Two unique fields, so no blanket attribution.** Roles and permissions each have one unique
field, so their forms map any 409 to `name`. This form must not: a conflict may concern `email`
**or** `username`. The API names which (`A user with that email already exists.`), so the generic
inference in `api-error.ts` is correct here and is used unchanged. Two tests assert each conflict
lands on its own field and leaves the other valid.

Run 015's walkthrough predicted exactly this, and it held.

**The password field exists only when creating.** An edit that carried a credential would put it
in a general-purpose body; changing one is its own dialog (D-9). A test asserts an edit
submission contains no `password` key at all.

**Password change asks for no current password.** It is an administrator action, not a reset. A
test asserts no such field exists.
