## Security review

**Uniform failure, verified byte-for-byte.** One message, one status, for all three causes. A
live comparison confirmed the three response bodies are identical — not merely similar. Had the
inactive case returned "account disabled", an attacker could enumerate valid accounts.

**Timing parity, measured.** The absent path runs a bcrypt verify against a dummy hash. Measured
0.19s vs 0.20s. Without it the difference would be roughly 5ms vs 200ms, which is trivially
detectable and would undo the uniform message entirely.

**Fail-fast on the secret.** Verified live. A default signing key is the kind of convenience that
makes every deployment that forgot to configure one silently forgeable.

**Order of checks.** Blank input short-circuits before any lookup. Permissions are resolved only
after credentials pass — a test asserts the resolution query is never called on a failed login,
so a failed attempt cannot be used to probe the permission graph.

**Claims carry no credential.** Verified by decoding a real token: no hash, no plaintext.

**The hash-bearing read model is separate.** `UserReadModel` still has no `passwordHash`;
`AuthUserReadModel` exists solely for verification. Widening the general read model would have
been the easy path and would have put a hash one careless `select *` away from every user
response.

## Observations — no action taken

**The dummy hash is a real bcrypt hash committed in source.** It is not a credential for anything
— it is a hash of a value no one knows, existing only to consume comparable CPU time. Worth the
comment it carries, so nobody mistakes it for a secret or "cleans it up".

**Token staleness is now a live property of the system.** Permissions are embedded at login, so a
revocation does not take effect until the token expires (default 1h). That is D-2's accepted
trade-off and the reason `permission-resolution` deliberately has no cache — the uncached query
remains the source of truth for anything that needs immediacy. `route-protection` will have to
choose between claims and a live lookup, and that choice belongs to that work item.

**No lockout or rate limiting.** Nothing in `docs/scope.md` asks for it, and adding it would be
scope creep — but an unthrottled login endpoint is worth naming, because uniform errors and
timing parity resist enumeration while doing nothing against brute force.

## Verdict

**Ready for completion.** 339 tests pass, lint clean, build succeeds. The enumeration-resistance
properties were verified by measurement rather than assertion, and the fail-fast was verified by
actually starting the app without a secret.
