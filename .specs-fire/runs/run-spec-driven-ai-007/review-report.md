# Code Review: Effective Permission Resolution

The security core of the module. Reviewed with one question in front: **can any revoked access
still resolve?**

## Findings Fixed

None. No defects surfaced in review or verification.

## Correctness review

**All four gates present and independently effective.** Verified by deactivating one hop at a
time with the others active. Gate 4's isolation is the strongest evidence: the link row was
confirmed still `ACTIVE` in the database while the permission's own `INACTIVE` status excluded
it, so the gates cannot be collapsing into one another.

**No user→permission path exists.** The SQL joins through `Role` and `RolePermission` only.
FR-AC2 is structural here, not a rule someone has to remember — there is no query that could
grant a permission directly to a user.

**`INNER JOIN` on Role gives FR-AC4 for free**, since a null `roleId` matches no rows. A test
and a live check assert it anyway rather than relying on a reader noticing the join semantics.

**Existence is separated from resolution.** 404 for a non-existent user, 200 with `[]` for an
existing but unprivileged one. A caller cannot mistake a typo'd id for a legitimate deny.

**Resolution agrees with the assignment slice.** Both filter links on `entityStatus = ACTIVE`,
so `GET /role/:id/permission` and resolution cannot disagree about what is granted — gate 3's
live check exercised exactly that path via D-8 removal.

## Observations — no action taken

**Raw SQL rather than Sequelize associations.** Deliberate: four independent status predicates
across three joins expressed through `include`/`where` would be considerably harder to read and
to audit, and this is the query most in need of being auditable. The cost is that it is not
type-checked against the models — `SchemaContract.spec.ts` and the live checks are the
compensating controls.

**`checkuserpermission` resolves the whole set then tests membership.** One query rather than a
targeted `EXISTS`. Simpler, and the set is small; a targeted query would be a micro-optimisation
on a path that is about to be fronted by JWT claims anyway.

**No caching, deliberately.** A revoked permission takes effect immediately. Worth noting that
`authentication-login` will embed permissions in a token and therefore *will* introduce
staleness until reissue — that is D-2's accepted trade-off, and it is that work item's job to
state it, not this one's.

**Case-sensitive, exact matching.** `PROJECT.CREATE` and `project` both deny. Permission names
are identifiers; loose matching in an authorization check is how prefix-matching bugs become
privilege escalation.
