## Reusability review — the point of this item

**The DataTable's props were designed against all three screens before it was built.** Each is
expressible today:

| Screen | Uses |
|--------|------|
| Permissions | search, status filter via `toolbar`, sort by name, row actions |
| Roles | the same, plus a create action in the empty state |
| Users | the same, plus a role filter in `toolbar` and more columns |

Nothing in those requires a fork. The `toolbar` slot is what absorbs per-screen filters without
the table needing to know about roles or statuses.

**Filtering, sorting and pagination are all controlled and server-side.** The table holds no
data state of its own beyond column visibility. That matters because the API paginates — a table
that sorted its own page would silently sort one page rather than the set, which looks correct
and is wrong.

**State precedence is explicit**: error → loading → empty → table. Asserted by a test that
supplies an error with empty data.

## Accessibility review

- Every component has an axe assertion **in both themes**, not just light
- The error in `FormField` is linked by `aria-describedby` and carries `role="alert"` — red text
  that is not associated with its field is invisible to a screen reader
- `aria-sort` reflects the active sort on the column header
- `StatusBadge` always renders the word; colour is decoration
- Radix supplies focus trapping and restoration for the dialog, asserted rather than assumed

## Observations — no action taken

**`DropdownMenuCheckboxItem` labels columns by their `id`** ("status", "name"). Fine for these
screens where ids read as words; a screen with an id like `roleName` would show that verbatim. If
that becomes awkward, the fix is a `meta.label` on the column definition — noted rather than
pre-built.

**`ConfirmDialog` takes `pending` but does not own the mutation.** The calling screen wires it to
its own mutation state. That keeps the dialog dumb and reusable, at the cost of each screen
remembering to pass it — the screens' own tests should cover that.

**Overlay tests are slow** (~7s for the menu interaction). It is Radix under jsdom, not the test.
Worth knowing before adding many more overlay interaction tests.

**`PermissionGate` defaults to hiding.** Before sign-in the claims are empty, so gated controls
are hidden rather than flashing and disappearing. The comment states plainly that this is
usability, not security.

## Verdict

covers every state FR-UI7 requires and every table behaviour FR-UI8 lists, and the three screens
can be built from it without forking anything.
