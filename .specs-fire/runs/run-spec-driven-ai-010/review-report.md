## Security review

**Default deny, and it is tested from both directions.** A route with no declared permission is
refused even for a caller holding everything, and a scan asserts every route-bearing controller
declares something. The failure mode this prevents — a new route quietly reachable by any
authenticated caller — is the most likely way this module would develop a hole.

**Global guards with explicit exemptions.** Per-route opt-in would mean a forgotten decorator
leaves a route open; global-with-`@Public()` means a forgotten decorator leaves a route *closed*.
Only three exemptions exist: login (a token cannot exist yet), health, and Swagger.

**401 and 403 are distinct, verified live.** Absent, malformed, and expired tokens are 401 with
one message that leaks nothing about which. A valid identity missing a permission is 403 and
names the permission — useful to an operator, and not a disclosure, since the caller already
knows what they attempted.

**The guards do not reimplement resolution.** They read claims produced by the shared query at
login, so FR-AC3's four gates cannot drift between what login granted and what enforcement
allows.

**Names are cross-checked against the seed.** A `@RequiresPermission` the catalogue does not
create would lock the administrator out with no API path to fix it. A test compares the two.

## The staleness trade-off — stated, not buried

Reading permissions from claims means **a revocation does not take effect until the token is
reissued** (default 1h). This is D-2's design, and the alternative — a resolution query per
request — would contradict it and add a database round trip to every call.

What follows from that choice, and should be understood before this module is depended on:

- Removing a permission from a role, deactivating a role, or deactivating a user does **not**
  immediately stop an already-issued token.
- Anything needing immediate revocation must call `GET /user/:id/permission`, which is uncached
  precisely so it can serve that purpose.
- `JWT_EXPIRES_IN` is the lever that narrows the window.

`permission-resolution` deliberately has no cache for this reason; that decision and this one
are two halves of the same trade-off.

## Observations — no action taken

**`/user/:id/permission` requires `user.view`.** It exposes a user's effective permissions, which
is user data, so the same permission that lists users governs it. Arguably it deserves its own
name; `user.view` is defensible and avoids inventing a permission the scope does not imply.

**No route requires more than one permission.** Nothing in the scope needs conjunctions, and a
single name per route keeps the mapping auditable at a glance.

**The guards trust the token's signature, not its contents' freshness.** That is the trade-off
above. They do not, for example, re-check that the user is still active — a deactivated user's
existing token keeps working until expiry. Worth naming explicitly because FR-U7 prevents
*login*, not the continued use of a token issued before deactivation.
