# Code Review: Login and Session Handling

Token handling in a browser is a security decision, so the review weighted that above layout.

## Findings Fixed

| # | Finding | Severity | Action |
|---|---------|----------|--------|
| 1 | Two tests asserted a state that cannot be observed through the provider — one failed, and one **passed for the wrong reason** | low | Both rewritten to test the branch directly with a controlled auth state |

## Security review

**The uniform failure message is passed through untouched.** The API returns one message for an
unknown user, a wrong password, and a deactivated account (run 008). The form shows
`login.error.message` verbatim — no client-side elaboration, no "user not found". Adding help
here would rebuild the enumeration oracle the API spent effort avoiding.

**The password cannot reach a URL.** It is sent in the body; a test asserts the request URL does
not contain it. It is never written to storage and never logged.

**401 and 403 do different things**, and both are tested: 401 clears the session and redirects;
403 leaves the user signed in with the token intact. Conflating them would sign someone out for
lacking one permission.

**Sign-out clears the query cache.** Without it the next person on a shared browser sees the
previous user's data from cache — a real leak, and a test pins it.

**Claims are decoded, not verified**, with a comment saying so. A browser cannot check a
signature meaningfully, and treating decoded claims as proof would be a category error. They
decide what to show; the API decides what is permitted.

**An expired token is discarded before use**, so a stale session does not spend a guaranteed 401
and then bounce.

**Storage failure is survivable.** Private browsing throws on `localStorage` access; the session
simply does not persist across a refresh rather than the app crashing.

### The D-10 trade-off, and what it obliges

Browser storage means any script on the page can read the token. Two things are therefore
requirements, verified by grep rather than assumed:

- **no `dangerouslySetInnerHTML`** anywhere in `src/` — 0 occurrences
- **no third-party script tags** — 0 occurrences

These need to stay true. If a later screen renders API-supplied HTML, the token becomes
extractable through any stored-content injection.

## Observations — no action taken

**The guard is client-side by necessity.** Next middleware cannot read `localStorage`, so
`RequireAuth` runs in the browser. Consequence: the server renders the shell for `/` before the
redirect. Verified this leaks no data — 0 occurrences of any seeded value — because markup is not
data and every fetch requires the token.

**`AppChrome` decides public routes by a literal path list.** Fine at one entry; if public routes
multiply it will want a better rule than an array.

**`tokenRef` holds the token rather than state.** Deliberate: the api-client seams are registered
once and read the ref, so they do not need re-registering on every change.

**No refresh-token flow**, because D-2 does not define one. Expiry means re-login, handled
cleanly rather than left as a broken screen. Stale permissions until reissue remain the accepted
trade-off from run 010.
