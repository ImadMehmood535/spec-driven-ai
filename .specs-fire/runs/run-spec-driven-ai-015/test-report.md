## The two pieces of copy that carry real information

**Deactivating a role** states the consequence that is invisible on this screen:

> "Users keep the Developer Admin role, but it will grant them no permissions until it is
> reactivated."

FR-AC3 excludes everything reached through an inactive role. Nothing on the roles table shows
that, so the dialog has to.

**Removing a permission** reflects D-8 rather than implying erasure:

> "project.create will no longer apply to anyone with the Developer Admin role. You can assign it
> again later."

There is deliberately **no separate reactivate control** — re-adding is an ordinary assign, and
the backend reactivates the same row. Run 004's walkthrough asked for exactly this.

## Live verification of the D-8 cycle

Driven through the same endpoints the dialog calls:

```
GET    /role                              → 1 role
GET    /role/1/permission                 → 18 assigned
GET    /permission?entityStatus=ACTIVE    → 18 in the catalogue

DELETE /role/1/permission/1               → 200 {"linkStatus":"INACTIVE"}
GET    /role/1/permission                 → 17 assigned
POST   /role/1/permission {"permissionIds":[1]}  → 201
GET    /role/1/permission                 → 18 assigned

RolePermission rows throughout            → 18   (never 19)
```

The screen's remove-then-re-add path is therefore proven against the real backend, not only
against mocks.
