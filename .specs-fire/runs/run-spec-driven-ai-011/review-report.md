Every later work item must import these rather than re-derive them. The error normaliser matters
most: without it each screen would interpret raw status codes, and the 401-vs-403 distinction
would be re-litigated per form.

## Security review

**401 clears the session; 403 does not.** The client calls the unauthenticated handler only for
401. Treating them alike would sign a user out for lacking a single permission — a real failure
mode, and one a test pins in both directions.

**The auth seam holds no token yet.** `ui-auth` owns storage (D-10). The client takes a getter,
so that decision lands in one place rather than being spread across call sites.

**No token is written anywhere in this run** — nothing to leak yet, and the seam is designed so
the leak surface stays at one file.

## Observations — no action taken

**4xx are not retried.** Retrying a 403 or 404 delays the error and makes the UI feel broken.
Only `network` errors retry.

**The field inference in `api-error.ts` reads the API's prose** ("A user with that email already
exists.") to decide which field a form should highlight. Fragile if the API's wording changes,
but confined to one function with tests naming each mapping — better than each form doing its own
string matching. If it ever breaks, it breaks in one visible place.

**`ThemeToggle` renders a stable icon until mounted.** The server cannot know the resolved theme;
without this there is a hydration mismatch. The `aria-label` still reflects the action.

**Navigation links point at `/users`, `/roles`, `/permissions`, which do not exist yet.** They
404 until the screen work items land. Acceptable for a scaffold, and the shell is what those
items build into.
