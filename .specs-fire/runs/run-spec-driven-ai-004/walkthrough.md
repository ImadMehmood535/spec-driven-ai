# Implementation Walkthrough: Role Management Slice

## Summary

Roles can be created, viewed, listed, updated, and activated/deactivated over HTTP. Same shape
as the permission slice, verified live. 201 tests pass.

Assigning permissions to a role (FR-R5) is the next work item — it needs the RolePermission
relationship, so it is deliberately not here.

## What landed

20 files mirroring the permission slice — `Role` aggregate, repository, query class, persistence

registration.

## Key Implementation Details

### 1. Generated by substitution, then actually reviewed

The slice was produced by substituting names in the permission slice, which reproduces structure
correctly and **semantics not at all**. Left unreviewed it would have shipped a Swagger contract
telling consumers a role is named `project.create`, and a `Role.rename` documented as "the
action this role grants".

Every generated file was read afterwards. That review produced all three findings in
`review-report.md`. Worth remembering for `user-crud`, which is *not* a candidate for this
technique — it has credential handling the other slices do not.

### 2. Deactivating a role does not cascade

The work item warned about this specifically. Nothing in the slice deactivates a user or a link
when a role is deactivated; FR-AC3 handles the consequence at resolution time by excluding
permissions reached through an inactive role.

Proven two ways: a test asserting `IRoleRepository` exposes no method that could cascade, and a
live check confirming user and link counts stayed at 0 after a role was deactivated.

### 3. Role names are human-readable, not action names

`docs/scope.md` §5 gives "Developer Admin". Every Swagger example and test fixture had to move
off the permission slice's `project.create` style — the single largest source of corrections.

## Decisions Made

| Decision | Choice | Rationale |
|----------|--------|-----------|
| Slice generation | Substitute from permission, then review every file | Fast for identical structure; the review is non-optional and produced 3 findings |
| No shared CRUD base class | Keep the duplication | Roles and permissions diverge — roles gain permission assignment. Coupling them now would have to be undone |
| No-cascade proof | Assert the repository's method set | Adding a cascading method should break the test and force a deliberate decision |

## Deviations from Plan

None. The plan anticipated the substitution-plus-review approach and the no-cascade requirement.
