# Design: Credential Verification and JWT Login

> Checkpoint 1 self-served under the standing instruction to run the loop autonomously.

## Summary

Verify credentials and issue a JWT carrying identity and effective permissions. Satisfies
FR-U6, FR-U7, and D-2.

## Scope

**In Scope:** one login route; `bcrypt` verification; JWT signing with claims from
`permission-resolution`; fail-fast on a missing `JWT_SECRET`; uniform 401s; body redaction.

**Out of Scope (D-2):** refresh tokens, logout, revocation, password reset. Each is a scope
change per §10. Token *verification* in a guard is `route-protection`.

## Key Decisions

| Decision | Choice | Rationale |
|----------|--------|-----------|
| Library | `@nestjs/jwt` | Recorded in `tech-stack.md` |
| Identifier | Email **or** username in one field | The scope names both as identity; forcing a choice would be arbitrary |
| Failure response | One 401, one message, for every cause | Distinguishing "unknown user" from "wrong password" hands an attacker a user-enumeration oracle |
| Inactive user | Same uniform 401 | FR-U7, with no hint the account exists |
| Timing | Verify against a dummy hash when the user is absent | Otherwise response time reveals whether an account exists |
| Claims | `sub` (globalUId), `username`, `role`, `permissions` | D-2; lets `route-protection` authorize without a query per request |
| Secret | From config; **app refuses to boot without it** | A default secret is worse than a crash |
| Lifetime | `JWT_EXPIRES_IN`, default `1h` | Config, not code |

## Technical Approach

```
POST /auth/login { identifier, password }
  └─ LoginCommandHandler
       ├─ userQueries.findAuthByIdentifier(identifier)   email OR username, incl. hash + status
       ├─ absent?  → verify against DUMMY_HASH, then throw UnauthorizedError   (timing parity)
       ├─ hasher.verify(password, user.passwordHash)  → false → UnauthorizedError
       ├─ user inactive? → UnauthorizedError            (FR-U7)
       ├─ permissions = resolution.findEffectivePermissionNames(user.id)
       └─ jwt.signAsync({ sub, username, role, permissions })
            └─ LoginResponse { accessToken, expiresIn }   no user object, no hash
```

The auth lookup is a **separate query** from `UserQueries`, because it must return the
`passwordHash` — which `UserReadModel` deliberately does not have. Keeping it separate means the
general read model stays hash-free.

## Security Considerations

- **Uniform failure.** One message, one status, for unknown user / wrong password / inactive.
- **Timing parity.** A bcrypt verify runs even when no user was found, so absence is not
  detectable by response time.
- **No secret default.** `JWT_SECRET` missing → the module throws at construction.
- **Redaction.** The login body contains a password; run 001's redaction covers `password`, and
  a test asserts the plaintext never reaches stdout.
- **Claims carry no credential.** No hash, no password, ever.
- **Inactive users cannot authenticate** even with correct credentials (FR-U7).

## Risks & Mitigations

| Risk | Impact | Mitigation |
|------|--------|------------|
| Error messages differing by cause | User enumeration | One `UnauthorizedError` message; tests assert all three paths produce identical bodies |
| Response-time difference on unknown user | User enumeration | Dummy-hash verify on the absent path; documented in code |
| Insecure default secret | Forgeable tokens | Fail fast at construction; a test asserts it throws |
| Stale permissions in a long-lived token | Revocation not taking effect until expiry | Accepted per D-2 — stated in the walkthrough, and lifetime is configurable |
| Plaintext password in logs | Credential disclosure | Redaction + an explicit test |
