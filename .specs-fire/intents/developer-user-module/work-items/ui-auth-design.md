# Design: Login and Session Handling

> Checkpoint 1 self-served under the standing instruction.

## Summary

The login screen and everything that follows from holding a token: session state, attaching it
to requests, redirecting unauthenticated users, reacting to expiry, and populating the claims
that `PermissionGate` reads. Satisfies FR-UI5 and the client half of FR-UI6.

Rated high because token handling in a browser is a security decision, not a layout one.

## Key Decisions

| Decision | Choice | Rationale |
|----------|--------|-----------|
| **Token storage** | `localStorage` | D-10: you chose client-side browser storage so a refresh does not force re-login. Accepted consequence below |
| Claims | Decoded from the JWT payload, **never verified client-side** | The client cannot verify a signature meaningfully; the API is the authority. Claims are read only to decide what to show |
| Expiry | Checked on load; an expired token is discarded before use | Avoids a guaranteed-401 first request |
| 401 handling | Clear session, redirect to login | The token is no longer usable |
| 403 handling | Show "not permitted", **stay signed in** | A missing permission is not a failed session |
| Sign-out | Clear token **and** the query cache | Otherwise the next user on the same browser sees cached data |
| Route protection | A client-side guard component | Next middleware cannot read `localStorage`; this is a browser-side session |

## The accepted risk, stated plainly

A token in `localStorage` is readable by **any script running on the page**. An XSS bug therefore
becomes a token disclosure.

That is D-10's accepted trade-off, and it makes three things requirements rather than preferences
in this project:

1. **No untrusted HTML is ever rendered** — no `dangerouslySetInnerHTML` anywhere.
2. **No third-party script tags** in the admin app.
3. **Token and query cache are cleared on sign-out**, so a shared browser does not leak.

The shorter `JWT_EXPIRES_IN` is, the narrower the window.

## Technical Approach

```
/login  (public)
  └─ LoginForm → POST /auth/login { identifier, password }
       ├─ 401 → one message; never reveals whether the account exists
       └─ 200 → store token → decode claims → redirect to /

AuthProvider
  ├─ reads the token on mount, discards it if expired
  ├─ setTokenGetter()          → the api-client seam from run 011
  ├─ setUnauthenticatedHandler() → clears session on 401
  └─ supplies PermissionsProvider with the claims

RequireAuth (wraps the app shell)
  └─ no session → redirect to /login
```

## Security Considerations

- **The login failure message is reused verbatim from the API**, which returns one uniform
  message for all three causes. The UI must not elaborate on it — adding "no such user" client-
  side would recreate the enumeration oracle the API deliberately avoids.
- **The password is never logged, never placed in a query string, never persisted.**
- **Claims are advisory.** `PermissionGate` hides controls; the API refuses the request.
- **Sign-out clears the query cache**, not just the token.

## Risks & Mitigations

| Risk | Impact | Mitigation |
|------|--------|------------|
| XSS reading the token | Session theft | No untrusted HTML, no third-party scripts; tests assert no `dangerouslySetInnerHTML` |
| Stale cache after sign-out | One user seeing another's data | Cache cleared on sign-out; test asserts it |
| Redirect loop on expiry | Unusable app | The guard redirects only when there is no session, and `/login` is outside the guard |
| A malformed token crashing the app | White screen | Decoding is defensive; anything unparseable is treated as no session |
| The UI being mistaken for the boundary | False sense of security | Comments and tests state it; the API enforces (run 010) |
