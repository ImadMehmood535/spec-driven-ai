# Design: Effective Permission Resolution

> Checkpoint 1 self-served under the user's standing instruction to run the loop autonomously.

## Summary

The capability the module exists to provide: given a user, determine which actions they may
perform. Satisfies FR-AC1–FR-AC4 and success criterion §9.6.

Resolution walks `User → Role → RolePermission → Permission`, and a deactivation at **any** of
those four hops removes the permission.

## Scope

**In Scope:**
- A query returning a user's effective permission names
- A check answering "may this user perform action X"
- Documented HTTP routes other modules can call (§9.6)
- All four FR-AC3 status gates, each independently tested

**Out of Scope:**
- Route guards (`route-protection`), JWT claims (`authentication-login`)
- Caching — no requirement, and staleness in an authorization path is a liability

## Key Decisions

| Decision | Choice | Rationale |
|----------|--------|-----------|
| Layer | Read side only: a query class, no repository, no aggregate | CQRS split; resolution never mutates |
| Query shape | **One** SQL query with joins | FR-AC1 says "determine whether a user has permission"; an N+1 across links would make every guarded request slow |
| Contract | Permission **names** (`project.create`), not ids | §5's example, and ids are meaningless to a calling module |
| Unknown user | **404**, not an empty set | "No such user" and "user has no permissions" are different answers; an empty set for a typo would read as a valid deny |
| Inactive user | Empty set | FR-AC3 |
| Null role | Empty set | FR-AC4 |
| Check endpoint result | `{ allowed: boolean }` plus the resolved set | Callers often want both; one round trip |
| Caching | None | Staleness in authorization is worse than a query |

## Technical Approach

```
GET /user/:id/permission                 → effective permission names
GET /user/:id/permission/check?name=X    → { allowed, permissions }

UserPermissionQueries.findEffective(userId)
  SELECT p.name
    FROM "User" u
    JOIN "Role" r             ON r.id = u."roleId"
    JOIN "RolePermission" rp  ON rp."roleId" = r.id
    JOIN "Permission" p       ON p.id = rp."permissionId"
   WHERE u.id = :userId
     AND u."entityStatus"  = 'ACTIVE'   -- gate 1: the user
     AND r."entityStatus"  = 'ACTIVE'   -- gate 2: the role
     AND rp."entityStatus" = 'ACTIVE'   -- gate 3: the link   (D-8 removal)
     AND p."entityStatus"  = 'ACTIVE'   -- gate 4: the permission
```

Four gates, one query. `INNER JOIN` on the role means a null `roleId` yields no rows, which is
FR-AC4 for free — but a test asserts it rather than relying on the reader noticing.

## Security Considerations

- **Every gate is independent.** The likeliest defect is implementing three of four. Each gets
  its own test with the other three active, so a missing gate cannot hide.
- **Existence is checked separately from resolution**, so a deactivated user returns an empty
  set (a valid deny) while a non-existent user returns 404. Conflating them would let a caller
  treat "unknown id" as "legitimately denied".
- **No caching**, so a revoked permission takes effect immediately. `authentication-login` will
  embed permissions in a JWT, which *does* introduce staleness — a trade-off that belongs to
  that work item, not this one.
- **Read-only.** No repository, no mutation path.

## Risks & Mitigations

| Risk | Impact | Mitigation |
|------|--------|------------|
| One of the four gates omitted | Revoked access still granted — a security hole that looks like working code | Four separate tests, each deactivating exactly one hop with the others active, plus a live check per gate |
| Duplicate names from the join | A caller seeing repeats, or a wrong count | `DISTINCT`; a test asserts uniqueness |
| 404 vs empty set confused | A typo'd id reads as a valid deny | Existence checked first; separate tests for both |
| Resolution diverging from the link filter in `role-permission-assignment` | The list endpoint and resolution disagreeing about what is assigned | Both filter on `entityStatus = ACTIVE`; a live test removes a permission and asserts it leaves the resolved set |
